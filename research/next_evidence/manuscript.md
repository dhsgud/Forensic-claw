# LLM 보조 Windows 포렌식의 직접 SQL 조회와 증거 추천

Comparing Direct SQL Lookup and Evidence Recommendations in LLM-Assisted Windows Forensics

## 요 약

Windows 브라우저의 다운로드 출처는 대상 프로필과 다운로드 행을 알면 History 데이터베이스에서 확인할 수 있다. 본 연구는 직접 SQL 조회로 충분한 조건과 추가 증거가 필요한 조건을 구분하고, Forensic-Claw가 부족한 증거를 추천할 수 있는지 평가하였다. Microsoft Edge와 Google Chrome에서 브라우저별로 다운로드 16건을 별도로 수집해 직접 조회를 검증하였다. 대상 데이터베이스와 행이 확인된 경우 SQL로 각 브라우저의 16건 모두에서 최종 출처를 확인하였다. 두 프로필에 동일한 행 번호가 있고 출처가 다르면 조회 결과만으로 대상 출처를 특정할 수 없었다. 수집 목록에서 대상 프로필을 확인할 수 있을 때는 SQL과 제안 방식이 모두 16건을 해결하였다. 대상 데이터베이스가 없는 조건에서는 두 방식 모두 보류하였다. 별도 실험에서는 조회 한도를 가정하여 고정 순서와 적응형 순서를 비교하고, 대규모 언어 모델이 제안한 정책을 재생하였다. 결과는 직접 조회가 가능한 때에는 이를 우선하고, 대상이 모호할 때에는 데이터베이스를 다시 검색하기 전에 출처를 연결할 증거를 확인할 필요가 있음을 보여준다.

**주제어** 대규모 언어 모델, Windows 디지털 포렌식, 증거 조회, 가설 검증, 브라우저 기록

## Abstract

The final source of a browser download can be retrieved directly from its History database when the originating profile and download row are known. We evaluated when this lookup is sufficient and when further evidence is required, and implemented evidence recommendations in Forensic-Claw. We collected 16 additional downloads per browser in Microsoft Edge and Google Chrome. Direct SQL identified the final source in all 16 trials per browser when the database and row were known. When the same row identifier referred to different sources in two profiles, SQL alone could not choose the relevant record. An acquisition manifest linking the target to its profile allowed both SQL and Forensic-Claw to resolve all 16 trials. Both methods abstained when the target database was withheld. Supplementary replay experiments compared fixed and adaptive query orders under assigned query limits and evaluated policies generated by a large language model. These results delineate direct retrieval from the problem of establishing which record belongs to the target event.

**Keywords** large language models, Windows forensics, evidence retrieval, hypothesis testing, browser history

## Ⅰ. 서론

Windows에서 Edge나 Chrome의 대상 프로필을 알고 있다면, 그 프로필의 History 데이터베이스에서 다운로드 행과 URL 체인을 연결하여 최종 주소를 조회할 수 있다. 남는 문제는 어느 데이터베이스의 어느 행이 조사 대상과 대응하는지 확인하는 일이다. 예를 들어 서로 다른 프로필에 행 번호가 같은 다운로드가 있고 파일의 바이트도 같다면, 각 데이터베이스에서 URL을 정확하게 읽어도 두 기록 중 어느 쪽이 대상인지 판단할 근거가 필요하다.

본 연구의 첫 질문은 직접 SQL 조회로 어디까지 판정할 수 있는가이다. 실제 Edge와 Chrome 기록을 사용해 대상 프로필이 확인된 경우, 대상이 모호한 경우, 수집 목록으로 대상을 확인할 수 있는 경우, 대상 데이터베이스가 빠진 경우를 비교하였다. 두 번째 질문은 자료에 접근 제약을 둔 경우 Forensic-Claw와 대규모 언어 모델이 어떤 조회 순서를 제안하는가이다. 이 비교는 직접 조회 검증과 분리한 보조 실험으로 수행하였다.

## Ⅱ. 관련 연구

국내 Windows 포렌식 연구는 통제한 사용자 행위와 그 결과 생성되는 기록을 연결해 검증하였다. Kim과 Lee는 행위 기반 윈도우 포렌식 검증용 데이터 세트를 구축하였다[1]. Choi 등은 Windows Event Trace Log의 포렌식 해석과 활용을 다루었으며[2], Kim과 Lee는 OneDrive 로그로 사용자 행위별 흔적을 비교하였다[3]. 본 연구에서는 같은 방식으로 다운로드 행위를 반복 실행하고, 브라우저 기록과 서버 기록을 대조해 판정 기준을 마련하였다.

Nisioti 등의 DISCLOSE는 공격 행위 사이의 관계와 검사 비용을 바탕으로 제한된 조사 예산에서 확인한 행위의 편익을 최대화한다[4]. Horsman은 수집 방법의 침습성을 고려한 확보 순서를 제안했다[5]. CAFE는 Windows의 여러 아티팩트가 특정 사건 주장을 어떻게 뒷받침하는지 비교한다[6]. 본 연구의 분석 단위는 브라우저 행위에 관한 명제 한 건이다. 같은 기록에서 읽을 수 있는 값이 무엇이고, 앞선 관측에 따라 다음 조회 대상이 달라지는지를 비용과 함께 평가한다.

검사 비용을 고려해 가설을 구분하는 문제는 능동학습에서도 다뤄졌다[7]. 본 연구에서 서로 다른 가설이 같은 판정으로 이어질 경우, 가설의 세부 차이까지 확인할 필요는 없다. 예를 들어 어떤 경로로 이동했든 최종 출처가 B라면 “출처 A에서 내려받았다”는 명제의 판정은 같다. 이때 현장 아티팩트가 실제로 어떤 값을 제공할 수 있는지는 별도로 확인해야 한다. NIST의 과학적 기반 검토도 기록의 생성 맥락과 관측 범위를 아티팩트 해석에 반영할 필요를 설명한다[8].

## Ⅲ. 연구 방법

### 3.1 Forensic-Claw에서의 다음 조회 추천

입력은 분석가가 설정한 가설, 관측 결과, 남은 예산이다. 각 가설에는 해당 명제의 판정과 자료별 예상 결과를 부여한다. 조회 결과가 들어오면 예상과 맞지 않는 가설을 제외한다. 남은 가설의 판정이 모두 같으면 지지 또는 반증을 반환한다. 지지와 반증이 함께 남으면 보류하고, 어느 가설도 관측과 일치하지 않으면 불일치를 표시한다.

추천기는 예산 안에서 가능한 다음 조회를 고려한다. 예상 결과별로 가설 집합을 나눈 뒤, 각 분기에서 남은 예산으로 추가 수행할 수 있는 조회를 탐색한다. 모든 분기에서 판정 가능한 가설 수를 합해 가장 큰 조회를 선택한다. 동률은 판정에 이르지 못한 분기를 포함한 전체 조회 비용으로 가른다. 가설의 가중치는 동일하게 두었다. Forensic-Claw의 CLI는 현재 판정, 남은 가설, 추천 조회와 비용, 예상 결과별 즉시 판정을 표시한다. 분석가는 실제 자료를 확인한 뒤 결과를 입력한다.

### 3.2 Windows 브라우저 기록 수집

Windows 11에서 Microsoft Edge 158.0.4370.33과 Google Chrome 157.0.8103.79를 각각 실행했다. 브라우저 제어에는 Playwright CLI 0.1.25를 사용했다. 회차마다 두 개의 새 브라우저 프로필을 만들어 총 8회씩 다운로드했다. 다운로드는 시작 URL과 리디렉션을 거쳐 두 최종 서버 중 하나에 도달했다. 두 서버는 같은 바이트를 반환하므로 파일 해시는 출처를 구분하지 못한다. 브라우저를 닫고 각 프로필의 History SQLite를 읽기 전용으로 조회해 완료 상태와 URL 체인을 확인했다. 절차상 지정한 프로필과 실제로 응답을 보낸 HTTP 서버의 로그를 판정 기준에 사용했다.

브라우저별로 세 회차에서 24건씩, 총 48건을 확보했다. 각 브라우저의 첫 회차 8건은 고정 순서 기준선을 정하는 데 사용했다. 후속 두 회차의 16건은 해당 순서를 선택하는 데 사용하지 않았다. 새 프로필과 HTTP 세션에서 자료를 다시 수집했으며, 실험 조건은 첫 회차와 같다.

### 3.3 직접 SQL 조회 기준선

앞 절의 자료와 별도로 브라우저마다 두 회차에서 16건을 추가 수집하였다. 두 프로필에 같은 바이트의 파일을 받되, 대조 프로필의 실행 순서를 반대로 배치해 같은 로컬 행 번호가 서로 다른 최종 서버에 대응하도록 하였다. 읽기 전용 SQLite 연결에서 `downloads.id`와 `downloads_url_chains.id`를 연결하고, 다운로드 완료 행에 대해 `chain_index`가 가장 큰 URL 한 건을 반환하였다. 조회에 사용한 테이블과 URL 순서의 의미는 Chromium 구현을 따랐다[9]. 이 결과를 전체 URL 체인의 마지막 값 및 실제 응답 서버와 대조했다. Forensic-Claw에 이 경로를 `download-source` 명령으로 추가하였다.

한 번 확보한 실제 조회 결과를 네 가지 자료 가용성 조건에서 재생하였다. ① 대상 프로필과 행 번호를 알고 DB를 열 수 있는 경우에는 해당 행을 직접 읽는다. ② 프로필이 불명확하면 양쪽 DB에서 같은 번호의 행을 확인하며, 두 출처가 다르면 보류한다. ③ 수집 목록에 대상과 프로필의 대응 관계가 있으면 해당 프로필의 행을 선택한다. 이 목록은 통제 실험에서 제공한 추가 자료다. ④ 대상 프로필은 알지만 해당 DB를 제공하지 않으면, 다른 프로필의 기록만으로 대상 출처를 확정하지 않는다. 같은 수집 목록을 활용하는 SQL 기준선을 따로 두어, Forensic-Claw와 동일한 정보로 비교했다.

### 3.4 조회 한도를 적용한 보조 실험

기본 조건의 조사 질문은 “대상 프로필에서 출처 A의 파일을 내려받았는가”이다. **조회 단위**는 한 자료를 확인할 때 차감하는 상대적 가중치다. 금액이나 초 단위의 실측값은 사용하지 않았다. 예를 들어 조회 한도가 3이면, 프로필 확인에 1단위를 쓴 뒤 나머지 2단위로 최종 URL을 확인할 수 있다. 반면 기본 조건에서 4단위가 필요한 전체 다운로드 기록 조회는 선택할 수 없다. 표 1은 보조 실험의 기본 가중치와 각 조회에서 얻는 정보를 보여준다.

| Query | Units | Observation |
|---|---:|---|
| File hash | 1 | Match to the reference payload |
| Browser profile | 1 | Target or comparison profile |
| Redirect route | 1 | Intermediate redirect category |
| Final URL | 2 | Final download source |
| Server record | 3 | Responding server or unavailable record |
| Full download record | 4 | Profile and final source together |
**<Table 1> Assigned query weights and obtainable observations**

두 가지 민감도 조건을 추가했다. 하나는 전체 다운로드 기록의 가중치를 4에서 2로 낮췄다. 다른 하나는 최종 URL을 2에서 4로 높이고 서버 기록을 3에서 2로 낮췄다. 프로필별 기록이 분리된 조건도 설정했다. 대상 프로필과 대조 프로필의 지정 출처가 다르므로, 확인한 프로필에 해당하는 보관 기록을 조회해야 한다. 이 조건에서 프로필 확인은 1단위, 각 보관 기록은 2단위다. 이 설정은 이미 수집한 기록에 자료 접근 조건을 적용한 재생 실험이다.

비교 대상은 사전에 정한 체크리스트, 개발 회차에서 모든 순서를 비교해 고른 최적 고정 순서, 반대 판정의 가설 쌍을 비용 대비 가장 많이 구분하는 탐욕 방식, 여러 단계의 조회를 함께 고려하는 제안 방식이다. 네 방식은 같은 자료와 판정 규칙을 사용했다. 조회 한도 1–5와 네 가지 비용·접근 조건에서 브라우저마다 1,280건씩, 총 2,560건의 정책 재생 결과를 얻었다. 정답 판정 건수와 함께 보류, 오판, 사용한 조회 단위의 합을 기록했다.

### 3.5 대규모 언어 모델 비교 설정

NVIDIA의 자체 호스팅 체크포인트 nvidia/Qwen3.8-Flash-Next-NVFP4-QAD[10]에 Pi를 통해 조회 정책을 요청했다. 기본 조건과 프로필별 기록 분리 조건에서 조회 한도는 3단위이고 추론 설정은 low였다. 모델은 평가 기록의 실제 관측값을 받지 않았으며, 다른 방식과 같은 가설표와 조회 가중치를 받았다. 입력마다 한 번 요청했고, 응답에는 조회 항목과 결과별 후속 조회를 JSON으로 기재하도록 했다. 생성된 두 정책을 Edge와 Chrome의 평가 기록에 각각 재생했다. 브라우저별로 모델을 다시 호출하는 대신, 같은 정책을 적용해 기록에 따른 결과 차이를 확인했다.

## Ⅳ. 실험 결과

### 4.1 직접 SQL 조회와 대상 식별

표 2는 브라우저별 16건의 결과다. Edge와 Chrome의 판정 건수는 모든 조건에서 같았다. 대상 프로필과 행을 안다면 직접 SQL 한 번으로 16건 모두의 최종 출처를 확인했다. 동일 번호가 서로 다른 출처에 대응하는 경우 Forensic-Claw는 프로필을 확인할 수 있는 수집 목록을 추천했다. 목록이 제공되면 SQL 기준선도 같은 16건을 판정했다. 목록이 없거나 대상 DB가 누락된 조건에서는 확인할 수 없는 출처를 보류하였다.

### 4.2 조회 한도별 판정

Edge와 Chrome에서 각 1,280건의 재생 결과를 비교했다. 동일 조건에서 조회 순서, 판정, 비용이 모두 일치했다. 표 3은 두 브라우저에 공통인 결과이며, 각 셀의 분모 16은 브라우저 한 종류의 평가 기록 수다. 뒤 숫자는 해당 16건에 사용한 사용한 조회 단위의 합이다.

|---|---:|---:|---:|---:|

기본 조건에서 제안 방식과 최적 고정 순서는 모두 프로필을 먼저 확인했다. 대조 프로필로 확인된 8건은 그 단계에서 반증했고, 대상 프로필의 나머지 8건에는 최종 URL 조회를 추가했다. 두 방식은 각각 조회 단위 합계 32에서 16건을 판정했다. 같은 예산에서 탐욕 방식은 12건을 판정하고 4건을 보류했다. 조회 한도를 4단위로 늘리면 탐욕 방식도 16건을 판정했고, 총 비용은 34였다. 전체 History를 저렴하게 조회할 수 있는 조건에서는 조회 한도 3단위에서 세 방식이 모두 같은 판정 건수와 비용을 보였다.

### 4.3 대규모 언어 모델의 조회 순서

프로필별 기록 분리 조건에서 모델은 프로필을 먼저 조회하고, 그 결과에 맞는 보관 기록을 확인하도록 했다. 이 정책은 16건을 조회 단위 합계 48에 판정했다. 기본 조건에서는 원응답에 설명이 붙어 JSON 전용 형식 검사를 통과하지 못했다. 부가 분석으로 코드 블록 속 정책을 추출해 그대로 재생하자 16건을 조회 단위 합계 32에 판정했다. 이 정책도 프로필을 먼저 확인하고 대상 프로필에서만 최종 출처를 조회했다. Edge와 Chrome에 같은 정책을 적용했을 때 두 브라우저의 결과가 일치했다. 각 조건의 판정 건수와 비용은 Forensic-Claw가 계산한 정책과도 같았다.

## Ⅴ. 고찰

직접 조회 결과에서 확인된 차이는 SQL의 검색 성능보다 입력 자료의 가용성에서 비롯되었다. 이미 대상 DB와 행을 확보한 경우에는 최종 URL을 직접 읽을 수 있다. 대상이 모호하면 두 DB의 조회를 모두 성공해도 어느 행이 조사 대상인지 결정할 수 없다. 수집 목록을 두 방식에 동일하게 제공했을 때 정확도는 같았다. Forensic-Claw가 추가한 것은 이 경우에 필요한 자료를 구체적으로 제시하고, 그 자료가 없으면 보류하는 판단 절차다.

기본 조건의 결과는 더 적합한 첫 조회를 고르면 이후 조회에 쓸 예산이 남는다는 점을 보여준다. 이 조건에서는 가설과 비용을 잘 반영한 고정 순서로도 충분했다. 프로필별 기록이 분리된 조건에서는 조회 순서 자체를 미리 고르는 일보다, 앞서 확인한 값에 따라 다른 자료를 선택하는 일이 중요했다. 이 경우 한 단계씩 고르는 방식으로도 모든 평가 기록을 판정할 수 있었다.

모델의 응답은 가설과 비용이 사전에 주어진 두 조건에서 적절한 조회 순서를 산출할 수 있다는 사례를 제공한다. 기본 조건에서는 정책의 내용과 인터페이스의 요구 사항이 달랐다. 사람이 읽을 수 있는 설명이 포함됐지만 자동 재생기는 지정된 형식으로 응답을 읽을 수 없었다. 이 실험에는 두 번의 LLM 호출만 포함됐으므로, 모델 간 우열이나 같은 모델의 반복 실행 안정성은 판단할 수 없다.

재생 실험에서 오판은 없었다. 자료가 등록된 가설 중 하나와 맞도록 수집됐고, 모든 비교 방식이 같은 판정 규칙을 사용했다는 점을 고려해야 한다. 실제 사건에서는 모형 밖의 행위가 등록 가설과 같은 관측을 만들 수 있다. 또한 조회 비용은 모형에서 설정한 단위이며 현장 조사 시간은 측정하지 않았다. 브라우저별 평가 회차는 새 프로필에서 실행했으나 동일한 여덟 조건을 반복했다. 두 제품 모두 Chromium 기반이므로 결과를 다른 브라우저 엔진의 아티팩트 구조에 일반화할 수 없다. 다른 사건 유형에 적용하려면 가설과 증거 관계를 정의하는 데 드는 비용과 실제 조회 시간을 함께 평가해야 한다.

## Ⅵ. 결론

Edge와 Chrome에서 대상 프로필과 다운로드 행을 알면 History의 직접 SQL 조회로 최종 출처를 판정할 수 있었다. 출처가 다른 두 기록이 같은 행 번호를 사용할 때에는 수집 목록과 같이 대상 프로필을 확인할 자료가 필요했다. 그 자료를 두 방식에 동일하게 주면 직접 SQL과 Forensic-Claw의 판정 결과는 같았다. 조회 순서를 조정하는 방법의 효용은 정보의 위치와 접근이 제약된 경우에 한정된다. 실제 적용에서 먼저 확인할 것은 대상 DB가 있고 그 행이 조사 대상과 연결되는지 여부다.

## 데이터 및 코드 가용성

정규화한 브라우저 기록, 직접 SQL 대조 및 자료 가용성별 결과, 실험에 사용한 사건 모형, 정책별 재생 결과, LLM 원응답과 채점 자료를 보존했다. 브라우저 기록 수집과 결과 재생 절차를 함께 제공한다.
